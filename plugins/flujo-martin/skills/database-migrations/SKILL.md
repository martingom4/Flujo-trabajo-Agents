# Database Migration Conventions

Standards for managing schema changes across Oracle (staging/production) and PostgreSQL (auth) in this project.

## When to Activate

- Adding, modifying, or removing database tables/columns/indexes
- Writing DDL scripts for Oracle or PostgreSQL
- Planning rollback strategies for schema changes
- Reviewing migration ordering and dependencies
- Working with schema initializers or Flyway/Liquibase scripts

## Dual-Engine Awareness

This project uses two database engines with different capabilities:

| Aspect | PostgreSQL (Auth) | Oracle (Staging/Production) |
| -------- | ------------------- | ---------------------------- |
| Purpose | Users, sessions, refresh tokens | Products, inventory, ETL, reports |
| DDL in transactions | Yes (transactional DDL) | No (implicit commit on DDL) |
| `IF NOT EXISTS` | Supported | Not supported natively |
| Identity columns | `GENERATED ALWAYS AS IDENTITY` | `GENERATED BY DEFAULT AS IDENTITY` (12c+) |
| Boolean type | Native `BOOLEAN` | `NUMBER(1)` with 0/1 |
| String type | `VARCHAR` / `TEXT` | `VARCHAR2` (max 4000 bytes) |

## Migration File Conventions

### Naming
```
V{version}__{description}.sql

Examples:
V1__create_users_table.sql
V2__add_mfa_columns_to_users.sql
V3__create_refresh_token_table.sql
```

### Structure
```sql
-- Description: Brief description of what this migration does
-- Author: your-name
-- Date: YYYY-MM-DD
-- Engine: Oracle | PostgreSQL

-- Migration SQL here
```

## Safe Migration Patterns

### Adding a Column
```sql
-- PASS: Nullable column — safe, no table rewrite
ALTER TABLE producto ADD (descripcion_larga VARCHAR2(2000));

-- CAUTION: NOT NULL column needs a default
ALTER TABLE producto ADD (activo NUMBER(1) DEFAULT 1 NOT NULL);
```

### Removing a Column
```sql
-- PASS: Two-phase removal
-- Phase 1 (deploy N): Stop reading/writing the column in application code
-- Phase 2 (deploy N+1): Drop the column
ALTER TABLE producto DROP COLUMN campo_obsoleto;
```

### Renaming a Column
```sql
-- Oracle
ALTER TABLE producto RENAME COLUMN nombre_viejo TO nombre_nuevo;

-- PostgreSQL
ALTER TABLE users RENAME COLUMN old_name TO new_name;
```

### Adding an Index
```sql
-- PASS: Online index creation (Oracle)
CREATE INDEX idx_producto_codigo ON producto(cod_producto) ONLINE;

-- PASS: Concurrent index creation (PostgreSQL)
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
```

### Modifying a Column Type
```sql
-- CAUTION: May require table rewrite on large tables
-- Prefer creating a new column, migrating data, then dropping old column
ALTER TABLE producto MODIFY (nombre VARCHAR2(500));
```

## Rollback Strategies

### Oracle (No Transactional DDL)
- DDL commits implicitly — cannot be rolled back in a transaction
- Always write a paired rollback script for each migration
- Test rollback scripts in QA before production

```sql
-- Migration: V5__add_column.sql
ALTER TABLE producto ADD (nueva_columna VARCHAR2(100));

-- Rollback: R5__add_column.sql
ALTER TABLE producto DROP COLUMN nueva_columna;
```

### PostgreSQL (Transactional DDL)
- DDL can be wrapped in a transaction
- Flyway/Liquibase will roll back on failure automatically

## Anti-Patterns

- **Never** modify a migration that has already been applied — create a new one
- **Never** use `DROP TABLE` without confirming the table is unused in all services
- **Never** add `NOT NULL` without a `DEFAULT` on an existing table with data
- **Never** run DDL migrations during peak traffic on Oracle (implicit locks)
- **Never** assume column order — always specify column names in `INSERT`

## Schema Initializers

For Oracle schemas managed via `ApplicationRunner`:

```java
// PASS: Catch connection errors, log WARN, don't block startup
@Override
public void run(ApplicationArguments args) {
    try {
        jdbcTemplate.execute(ddlScript);
        log.info("Schema initialized successfully");
    } catch (DataAccessException ex) {
        log.warn("Could not initialize schema — DB may be unavailable: {}", ex.getMessage());
    }
}
```

## Pre-Migration Checklist

1. Identify which engine (Oracle/PostgreSQL) the migration targets
2. Write the migration SQL with engine-specific syntax
3. Write a corresponding rollback script (especially for Oracle)
4. Test on a copy of production data if modifying existing tables
5. Verify no application code depends on the old schema during deployment
6. Coordinate with deployment order if multiple services consume the schema

**Remember**: Schema changes are among the riskiest operations. Plan for failure and always have a rollback path.
